01 · Overview

One question, answered by recomputation

Can a shared data record be compact, exactly recoverable, provably unaltered and traceable to its makers, without trusting whoever stores it? BioChain answers yes by making every property something the reader checks for themselves.

Determinism is protocol law

Quaternions travel as exact 8-bit fixed-point codes, consensus code reads raw integers, and independent runs must produce bit-identical output.

Logic is configuration, not code

A codex, the model that drives compression, is a program in a closed, jump-free instruction set. It always halts, and a malformed one is rejected before it runs.

Count everything shipped

A record's value is scored against the total of seed, codex, residual and commitment bytes, so hiding data inside the model gains nothing.

03 · How to use BioChain

From sign-in to a traced, transferred biochain

Everything runs in your browser. There is no application server, and the only server-side code is the Firestore security rules. You need a Google account. Nothing else needs installing.

Sign in with Google

Open the platform and choose Continue with Google. Your Firebase account becomes the anchor for your identity and keys.

Where: login.html

Commit your Identity

On first sign-in, enter a private identity seed phrase. BioChain folds its SHA-256 into a 64-bit geometric vector and XORs it with a hash of your account ID to produce your permanent Identity ID. A live preview shows the ID and its identicon before you commit.

This is one-way. Once committed, the rules freeze your Identity ID, seed and geometric vector forever. The ID is a stable public handle, not a secret.

Where: login.html · one-time setup

Create a signing key

In the Keys tab, give the key a label and choose Create signing key. Your browser generates an ECDSA P-256 key pair with WebCrypto. The public key goes to the shared registry, and the private key is stored in a document only you can read. Every certification and transfer you make is signed with this key.

Where: Operations Console → Keys · revoke a key here too. Revocation is permanent and invalidates everything it signed.

Grow a biochain

In Grow & Certify, add a title, paste your text, and choose Grow (preview). Growing is pure computation with no network: the text is split into 720-byte chunks, rank-coded, framed, and committed to a Merkle root and a chiral weave. The preview shows the chain ID (BC-…) and its measured value.

Limit: up to 60,000 bytes of input, so a record fits in one Firestore document.

Certify & publish

Choose Certify & publish. Your key signs a GROWN/1 statement and the chain is written with you as grower and owner, plus the first lineage entry. Tick listed to show it in the marketplace.

Verify, rate and list in the Marketplace

Any chain can be verified, which rebuilds it byte for byte in your browser. Any signed-in user can rate a chain once. As owner you can list or unlist your own chains.

Send a biochain (always free)

In Transfers, enter the chain ID and the recipient's user ID, then choose Send. This signs a TRANSFER/1 record with price: 0, stamped with the chain's current sequence number. It waits as pending.

Tip: the recipient's user ID is shown at the top of their console.

Accept or decline an incoming transfer

Recipients see pending transfers under Incoming. Accept moves ownership to you and advances the chain's sequence by one, so the same transfer can never be applied twice. Decline leaves the owner unchanged. No transfer document is ever deleted, and together they are the chain's lineage.

Trace the lineage

In Trace, enter any chain ID. traceBiochain verifies the certification, every hop's transfer attestation in date order, and the chain's full integrity, then returns them together.

Roles

Everyone starts as a MEMBER, and any signed-in member can grow, transfer and rate. ADMIN and OPERATOR roles gate only the operations consoles and the weight of a rating (ADMIN counts 3×, OPERATOR 2×). Roles come only from a root-admin list editable in the Firebase console, or from grants written by an ADMIN. Nobody can grant a role to themselves. Admins grant roles in the Operations Console's Roles tab, which only admins can see.

04 · How it works

4.1

The SHD-CCP packet: seven fields, exactly 64 bits

Every object in BioChain, whether an instruction, a compressed chunk or a commitment, is built from one 64-bit word. Select a field to see what it holds.

bit 63bit 32
bit 31bit 0

No free floats on the wire

Quaternion components are signed 8-bit codes. Code −128 normalizes to −127, so the range is symmetric. Worst measured error: 0.003937, within the 1/254 bound.

Parity catches any flipped bit

The self-test flips each of the 64 bits in turn and catches all 64.

The layout is pinned

A golden ABI hash is computed over the field map, and any change to the layout changes it. crystallize(chunk) folds any byte string into one packet.

4.2

Growing a biochain

Chunk

Split input into 720-byte chunks. Each starts with a fresh model, so any chunk decodes on its own.

Predict

An order-2 model ranks candidate next bytes by count from the two bytes before.

Correct

Store only the byte's rank as an Elias-gamma code, so well-predicted bytes cost as little as 1 bit.

Frame

Crystal packet + 32-bit residual length + residual. The stream describes itself.

Commit

Merkle root, chiral weave and per-packet parity: three independent checks.

Merkle root

Each leaf binds a chunk to its position: ℓᵢ = SHA256(i ‖ SHA256(cᵢ)). Leaves are hashed in pairs up to one root R.

Chiral weave

The ordered product of each chunk's unit quaternion, W = q̂ₙ ⋯ q̂₁. Multiplication doesn't commute, so swapping two chunks changes the result.

Parity

Every packet's parity bit is checked before its frame is decoded.

Chain ID binds the first two commitments: chainId = "BC-" + SHA256(R | W)[0:24]. verifyIntegrity rebuilds everything and fails at the first mismatch: parity → each chunk vs its leaf → Merkle root → chiral weave → token-engram stream. extendBiochain grows a child chain by epochs and never changes the parent.
4.3

Codexes and the value law

A codex is the model that drives compression, written as a program of packets in a closed instruction set with no jumps. It must open with GEAR, end with HALT, and contain only PRIME in between. The parser rejects a malformed codex before anything runs, and predictor work is fuel-metered on top of that.

OpcodeNameMeaning
1GEARHeader: chunk size (64–4096 bytes), model order (1–3)
2PRIMEOne pretrained entry: context, next byte, count
0HALTEnd of program

In the browser, deriveCodex keeps the 120 most frequent order-2 pairs. A codex is content-addressed (CX- + SHA-256 prefix), signed by its author (CODEX/1) and immutable once published.

Value scores a growth by how many bytes it recreates per byte it ships, counting everything a verifier needs:

value = recreated bytes / ( 8 + 8·|codex|/k + |residual| + 8·|chain| )

k is the number of growths a codex serves. Counting the codex closes the obvious loophole: a 528-packet codex stuffed with the corpus scores 0.97, below the honest 2-packet codex at 1.47.

Attunement checks that a codex carries real knowledge rather than a memorized copy, by testing on held-out text:

ε = 1 − |residualattuned| / |residualfresh|

A 400-entry codex cuts the residual from 3,350 to 1,457 bytes (ε = +56.5%). On random data it gives ε = −0.001, an honest null. Spread over 50 growths, its value reaches 3.29. That shared-dictionary effect is what the economy is designed to reward.

4.4

Token engrams and retrieval

An engram is a 64-bit fingerprint of a word. Each letter A–Z maps to a fixed 8×8 bit grid, and a token's engram is the XOR of its letters' grids. The shared test vector is engram("GEODESIC") = 5C896A4801C9C24C.

A biochain's engram index turns it into a library. Text is split into passages of up to 320 characters, each keyed by its engram. Queries match by Hamming distance, and the nearest passages come back verbatim, so recall never makes up text.

What the fingerprint captures

Because it XORs letter grids, an engram depends only on which letters appear an odd number of times. Anagrams collide and doubled letters cancel. The recalled text is always genuine, but the ranking is a lexical heuristic, not a measure of meaning.

The Language Studio (ADMIN) wraps this as a retrieval agent that can optionally pass recalled context to an external language model. Destroying a session logs only the turn count and a parity word, never the content.

4.5

Identity, signing keys and attestations

Identity ID

Fold₄ₓ₄ₓ₄(SHA256(seed)) ⊕ SHA256(uid)[0:8]. It is frozen forever once committed and serves as a stable public handle.

Signing keys

WebCrypto P-256 pairs, identified by K- + SHA-256(x | y). The private key sits in an owner-only document, and the public key is mirrored to keyRegistry.

Attestations

ATTEST/1 | keyId | keyVector | SHA256(content) | epochToken. They verify only against an active registry key.

Each operation signs its own typed statement (GROWN/1, GROWTH/1, CODEX/1, PAIR/1, TRANSFER/1), and the verifier rehashes it from the record's fields. A signature is therefore bound to the exact record, not merely to some content. Time is stamped as EPOCH.<window> in 3-hour windows, which stay stable offline.

05 · Security model

The rules are the boundary

All cryptography runs in the browser, so Firestore security rules are the only server-side enforcement. A guarantee holds against a hostile client only if the rules enforce it. Nothing whose history must survive can be deleted.

Hardening applied: four attacks, four fixes

Ownership replay

A previous owner re-submits an old accepted transfer to pull the chain back.

Fix: a per-chain transfer sequence. A transfer applies once, and only from the current owner at the current sequence.

Self-granted roles

A user writes role: ADMIN onto their own identity. The old HMAC role certificates were keyed by a public ID, so anyone could forge one.

Fix: roles come only from config/rootAdmins and ADMIN-written roleGrants.

Reversible revocation

An owner flips a revoked key back to active, reviving every attestation it signed.

Fix: registry status is one-way, and keys are born active.

Self-declared rater role

A rater claims ADMIN to triple their rating's weight.

Fix: the rules check raterRole against the rater's real role.

A 47-case emulator suite (tests/rules/) checks every attack and every legitimate flow, and all 47 pass. Run against the original rules, 25 fail. Run it with cd tests/rules && npm install && npm test (needs Java for the Firestore emulator).
Residual risks we're open about
  • Private keys live in Firestore, in owner-only documents, not on your device. Anyone who compromises the Firebase project or your Google account obtains the keys.
  • The lineage array is written by the client. The rules restrict which fields change on a hand-off, not what new lineage entries say. The transfers collection is the authoritative history.
  • Accept is two writes. A client that marks a transfer accepted and then stops leaves ownership unmoved. The pair is not atomic.
  • Records written before the hardening keep their old values. Ratings that claimed a false role keep that weight until edited.
06 · Reference mesh Simulation

The fully decentralized design

The Python reference stack simulates 9 nodes in three tiers that exchange records by gossip. Every node re-verifies every record itself and treats nothing it receives as trusted.

Tier 1

Biostrata (edge)

2 growers, one of them hostile. They author codexes and grow biochain claims.

Tier 2

HyperSim (mesh)

4 validators that gossip and independently validate every record, earning FLUX.

Tier 3

Spire Core

1 root anchor and 2 governors that run full replay, the twin attunement bench, crystallization and CRYST sequencing.

Validation processor

Each node samples 3 chunks per claim, chosen by hashing the Merkle root with its own name so each node picks differently, replays them against their leaves, and recomputes the value score. Sampling is probabilistic: a tampered residual was caught by 2 of 9 nodes through sampling, and with certainty by the core's full replay. Crystallization therefore always waits for full replay.

FLUX: a meter, not a currency

Earned at 1.0 per claim or codex validated and 0.1 per other record. It maps to a read quota: 5 FLUX unlocks 10 reads/min, 15 unlocks 30, 40 unlocks 60, and 80 unlocks 200. It never appears in any record, so it can't be transferred or traded.

CRYST: scarce, backed by measured value

CRYST issued = 100 × value × ε

Every validator recomputes the value, and two governors must agree bit for bit on ε. It is redeemable at 12 compute-seconds per CRYST. In the run, a claim with value 1.45 and ε 0.250 issued 36 CRYST. Replayed transfers and overdrafts were rejected everywhere.

Pump time

A gear counter any node computes identically: 720 frames per cycle, 12 sectors. Positions read PUMP.<cycle>.<sector>.<middle>.<inner>. For example, frame 437 is PUMP.0.7.43.6. Gear alignments define handoff windows (12 per cycle) and crystallization windows (ticks 6 and 12).

Chirality & the pairing rule

Every identity has a public hand, L or R. Crystallization needs at least 2 attesters of the hand opposite the grower's, so a grower can never attest its own growth. The genesis anchors must include one L and one R. The limits are stated plainly: chirality is structure, not cryptographic hardness, and ECDSA remains the lock.

Sharded engram storage

A chain is cut into segments (7 over 15 chunks) stored on 2 of 5 nodes. Quaternion multiplication is associative, so segment products rebuild the exact global weave (0.0 rad error). The chain rebuilds with a node dead, tampered shards are refused, and validation takes no identity argument.

Why order must be committed: XOR is commutative, so swapping chunks 2 and 5 leaves an XOR holonomy word unchanged. The chiral weave catches the same swap, moving by 1.771 rad. That is why browser records commit to the weave.
07 · Measured results

Only structured text beats break-even

Every one of the eight configurations round-trips losslessly. Value falls below 1 on random data whatever the codex, which is the correct result, because no model beats entropy. The codex-stuffing attack loses to honest compression.
